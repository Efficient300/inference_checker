# H200 Video Bench

Бенчмарк, который отвечает на вопрос: **сколько камер 1080p один GPU (NVIDIA H200) обрабатывает одновременно** при полном пайплайне анализа людей. Пайплайн включает декодирование, детекцию, трекинг, re-ID и распознавание лиц.

На выходе получается карта ёмкости. Для каждой комбинации «сценарий × FPS на камеру × точность моделей × режим идентификации» бенчмарк находит **N_max** — наибольшее число камер, которое система выдерживает. Также он показывает, какой ресурс заканчивается первым.

## Общая схема

```
data/videos/*.mp4 (1080p@25, H.264/H.265)
        │  ffmpeg -re -stream_loop -1 -c copy   (без перекодирования, на выделенных ядрах через taskset)
        ▼
MediaMTX (RTSP, TCP)  rtsp://127.0.0.1:8554/cam0 … cam{N-1}
        │
        ▼
┌───────────────────────── bench.run_matrix ─────────────────────────┐
│ для каждой комбинации матрицы:                                     │
│   find_n_max  ──evaluate(N)──►  PointRunner.run(combo, N)          │
│                                   │                                │
│                                   ├─ start_streams.sh N            │
│                                   ├─ K процессов-воркеров          │
│                                   │     (камеры делятся i % K)     │
│                                   ├─ Sampler: NVML + psutil, 1 Гц  │
│                                   └─ aggregate_point → passed?     │
│   limiting_resource(точка N_max+шаг)                               │
└────────────────────────────────────────────────────────────────────┘
        │
        ▼
results/<run_id>/<combo_id>.json  ──►  bench.report  ──►  REPORT_DRAFT.md + report/*.png
```

Важный принцип: **камеры всегда отдают 25 FPS, и декодируется каждый кадр**. До целевого FPS (5/10/15/25) поток прореживается уже после декодера. Поэтому NVDEC нагружен так же, как в реальной системе, а модели получают только часть кадров.

## Сценарии нагрузки

Каждый следующий сценарий добавляет к предыдущему одну стадию ([bench/config.py](bench/config.py), словарь `STAGES`):

| ID | Стадии | Что измеряет |
|---|---|---|
| S0 | только декодирование | потолок NVDEC |
| S1 | + `detect` | детекция людей (YOLO, TensorRT) |
| S2 | + `track` | ByteTrack на каждую камеру (CPU) |
| S3 | + `reid` | эмбеддинги внешности (OSNet) |
| S4 | + `face` | детекция лица (SCRFD) + эмбеддинг (ArcFace) |

В S0 кадры не копируются в тензоры и модели не загружаются: кадр считается обработанным, как только он прошёл прореживание.

## Путь кадра внутри воркера

Воркер — это отдельный процесс ([pipeline/worker.py](pipeline/worker.py)), который обслуживает группу камер. Внутри процесса работают потоки, и каждая GPU-стадия использует свой CUDA stream:

```
cam0 ─┐  CameraReader (поток на камеру)
cam1 ─┼─►  RTSP → NVDEC → FpsLimiter → копия NV12 в torch-тензор на GPU
camN ─┘            │
                   ▼
            DynamicBatcher "detect"  (межкамерный батч, ≤ queue_per_cam кадров на камеру)
                   ▼
   поток detect:   NV12→RGB → letterbox → TensorRT YOLO → NMS → боксы на CPU
                   ▼
   поток track:    ByteTracker[cam].update(боксы) → треки
                   │   IdScheduler выбирает треки для идентификации
         ┌─────────┴─────────┐
         ▼                   ▼
 DynamicBatcher "reid"   DynamicBatcher "face"
 поток reid:             поток face:
  roi_align кропы тел     квадрат головы → SCRFD → лучшее лицо
  → OSNet → эмбеддинги    → выравнивание по 5 точкам → ArcFace
         └─────────┬─────────┘
                   ▼
        кадр завершён → задержка = t_done − t_recv
```

### 1. Приём и декодирование — [pipeline/decoder.py](pipeline/decoder.py)

- `NvRtspDecoder` открывает RTSP через PyNvVideoCodec. Демультиплексор и декодер NVDEC работают так, что кадр остаётся в памяти GPU (`usedevicememory=True`).
- **Время приёма** `t_recv` — это момент получения пакета, из которого вышел кадр (сопоставление идёт по PTS). Задержка end-to-end отсчитывается от этого момента.
- Каждый декодированный кадр учитывается как `decoded`. Раз в секунду пишется **отставание от реального времени**: `(сейчас − t_первого_кадра) − n_декодировано / 25`. Если NVDEC не успевает, отставание растёт.
- `FpsLimiter` ([pipeline/fps_limiter.py](pipeline/fps_limiter.py)) решает, оставить ли кадр, **по номеру кадра, а не по часам**. Для этого используется рациональная дробь `target/source`, поэтому из 25 FPS ровно получаются 5/10/15/25. Если декодер отстаёт, выходной FPS падает пропорционально, и это видно в метриках.
- Выбранный кадр (`selected`) копируется в собственный NV12-тензор `[H·3/2, W]`, потому что буфер декодера переиспользуется. Затем кадр передаётся в `on_frame`.
- При обрыве, EOF или исключении в `Recorder` пишется событие, после чего идёт переподключение с экспоненциальной паузой от 0,5 до 5 с.

### 2. Динамический батчер — [pipeline/batcher.py](pipeline/batcher.py)

`DynamicBatcher` — одна FIFO-очередь на все камеры воркера. Батч отдаётся, как только набрано `max_batch` элементов **или** с момента появления первого элемента прошло `batch_timeout_ms`. Благодаря FIFO порядок кадров каждой камеры сохраняется.

Ёмкость очереди ограничена **на камеру** (`queue_per_cam`). Если у камеры уже лежит `queue_per_cam` необработанных кадров, новый кадр отклоняется и учитывается как **пропущенный (drop)**. Именно так перегрузка проявляется в метриках: очередь не растёт бесконечно, а кадры начинают теряться.

### 3. Детекция — [pipeline/detector.py](pipeline/detector.py), [pipeline/preprocess.py](pipeline/preprocess.py)

Весь препроцессинг выполняется на GPU с помощью torch:
- `nv12_to_rgb`: NV12 → RGB по BT.709 (limited range) в half-precision;
- `letterbox`: ресайз с сохранением пропорций до 640 (или 1280) и паддинг значением 114;
- TensorRT-модель ([pipeline/trt_runtime.py](pipeline/trt_runtime.py)); если батч больше `max_batch` engine, он режется на куски;
- `yolo_postprocess`: фильтр по классу person и `conf`, затем `batched_nms` из torchvision, обратный пересчёт координат в пиксели кадра 1920×1080, ограничение `max_det`.

RGB-кадры сохраняются в задаче, если дальше нужны кропы (S3/S4).

### 4. Трекинг — [pipeline/tracker.py](pipeline/tracker.py)

ByteTrack, по одному экземпляру на камеру. Состояние треков хранится как набор numpy-массивов. Фильтр Калмана (`BatchKalman`) делает predict и update сразу для всех треков камеры одной матричной операцией. Сопоставление проходит в три шага, как в оригинальном ByteTrack:

1. активные и потерянные треки ↔ уверенные детекции (`score ≥ track_thresh`), стоимость `1 − IoU·score`;
2. оставшиеся активные треки ↔ слабые детекции (`low_thresh ≤ score < track_thresh`);
3. неподтверждённые треки ↔ оставшиеся уверенные детекции.

Новые треки создаются из несопоставленных детекций со `score ≥ new_track_thresh`. Потерянные треки удаляются через `track_buffer` кадров (значение пересчитывается под фактический FPS). Сопоставление выполняет венгерский алгоритм `scipy.optimize.linear_sum_assignment`.

Трекинг идёт на CPU в одном Python-потоке на воркер, поэтому при сотнях камер он может стать узким местом. Его загрузка видна в метрике `stage_track`.

### 5. Выбор треков для идентификации — [pipeline/idsched.py](pipeline/idsched.py)

Идентифицировать каждый трек на каждом кадре дорого и бессмысленно. Поэтому `IdScheduler` (отдельный для re-ID и для лиц на каждой камере) выбирает треки по режиму:

| Режим | Поведение |
|---|---|
| `every_k_5` | трек идентифицируется на первом кадре, затем на каждом 5-м анализируемом кадре |
| `new_tracks_only` | трек идентифицируется, пока не подтверждён: для re-ID — получен эмбеддинг, для лиц — найдено лицо. Пока запрос в обработке, трек повторно не выбирается |
| `every_k_1` | худший случай: каждый кадр |

Для лиц можно отсечь мелкие фигуры параметром `face_min_person_h`. Значение `0` означает искать лица на всех треках, это худший случай.

### 6. Re-ID и лица — [pipeline/reid.py](pipeline/reid.py), [pipeline/face.py](pipeline/face.py)

Выбранные треки кадра отправляются в свой `DynamicBatcher`. Батч собирается **по кадрам** (до `id_frames_per_batch = 32` кадров), а кропы из всех кадров батча вырезаются одним вызовом `roi_align`.

- **Re-ID:** кроп тела 256×128 → нормализация ImageNet → OSNet → L2-нормированный эмбеддинг 512.
- **Лица:** квадрат верхней части бокса человека (`upper_squares`: ширина бокса, от верхнего края вниз) → кроп 640×640 → SCRFD. `scrfd_top1` декодирует выходы всех страйдов и берёт лучшее лицо на кроп. Если `score > conf`, лицо выравнивается по 5 ключевым точкам (similarity transform к шаблону ArcFace, `grid_sample`) → кроп 112×112 → ArcFace → эмбеддинг.

Эмбеддинги вычисляются по-настоящему и копируются на CPU, но дальше не используются. Поиск по галерее не входит в задачу бенчмарка.

### 7. Завершение кадра

У каждого кадра есть счётчик `pending` — число ожидаемых стадий идентификации (0, 1 или 2). Когда последняя стадия закончила работу, кадр считается **обработанным** (`done`) и фиксируется задержка `t_done − t_recv`. Кадр считается **пропущенным**, если:
- его не принял батчер детекции (переполнение очереди камеры);
- его запрос не принял батчер re-ID или лиц;
- стадия упала с исключением.

## Как измеряется одна точка

Точка — это одна комбинация матрицы при заданном N камер. Её прогон выполняет `PointRunner.run` из [bench/point.py](bench/point.py):

1. **Потоки.** `StreamManager` ([bench/streams.py](bench/streams.py)) запускает `streamer/start_streams.sh N`: по одному ffmpeg на камеру, клипы назначаются по кругу, а копии одного клипа сдвинуты по времени старта на 37 с. Затем менеджер ждёт через API MediaMTX, пока все `cam0..cam{N-1}` станут `ready`. В режиме `streamer.mode: external` потоки уже публикуются кем-то другим, и бенчмарк только проверяет их готовность.
2. **Воркеры.** Запускается `K = min(workers, N)` процессов (`multiprocessing` spawn). Камера `i` попадает в воркер `i % K`. Каждый воркер загружает engine, делает прогрев моделей на пустом кадре и отвечает `ready`. Таймаут инициализации — 600 с.
3. **Синхронный старт.** Родитель рассылает общие метки времени `t0`, `t_meas = t0 + warmup_s` и `t_end = t_meas + measure_s`. Время в процессах общее, это `time.monotonic()`.
4. **Прогрев и замер.** Воркеры читают потоки с момента `t0`. **В метрики попадают только кадры с `t_recv` в окне `[t_meas, t_end)`**: так прогрев (60 с по умолчанию) отбрасывается. После `t_end` ещё `drain_s` секунд дообрабатываются кадры, которые уже в пути.
5. **Сэмплер** ([bench/metrics.py](bench/metrics.py), `Sampler`) раз в секунду снимает:
   - через NVML: SM util, NVDEC util, VRAM, мощность, температуру, частоту SM, причины снижения частот (термо-троттлинг и power cap);
   - через psutil: общий CPU, трафик сети, CPU по группам процессов — `workers` (сумма и максимум по одному воркеру), `streamer` (ffmpeg + MediaMTX), `bench`. Нагрузку стримера можно вычесть.
6. **Сбор.** Каждый воркер пишет JSON со счётчиками по камерам и `.npy` с задержками. `aggregate_point` сводит всё в одну точку.
7. **Уборка.** Воркеры, потоки и временные файлы удаляются в любом случае (`finally`).

Внутри воркера раз в секунду также снимается глубина каждой очереди. Если камера не выдаёт кадров дольше `stall_timeout_s`, пишется событие `stall`.

## Критерии «выдержано» и валидность точки

### Прошла ли точка — `check_pass`

N камер считаются выдержанными, только если **одновременно** выполнены условия:

| Условие | Поле | Порог по умолчанию |
|---|---|---|
| FPS **худшей** камеры ≥ 95% целевого | `fps_min` | `min_fps_ratio: 0.95` |
| доля пропущенных кадров на **худшей** камере ≤ 1% | `drop_rate` | `max_drop: 0.01` |
| очереди не растут | `queue_slope` | `max_queue_slope: 0.05` |
| не было CUDA OOM | — | — |

`queue_slope` — это максимум из двух величин:
- наклонов (МНК) глубины каждой внутренней очереди, в элементах в секунду;
- наклона отставания декодера каждой камеры, переведённого в кадры в секунду. Эта величина ловит ситуацию, когда не успевает сам NVDEC и до батчеров дело не доходит.

Задержка (p50/p95/p99) **не является условием прохождения**. Она только записывается в результат.

### Валидна ли точка

Точка **невалидна** (`valid: false`, причина в `invalid_reason`), если в окне замера у какой-либо камеры был `error`, `eof`, `reconnect` или `stall`, если у камеры нет ни одного декодированного кадра или если стадия упала с ошибкой, отличной от OOM. Невалидная точка автоматически **повторяется один раз**. Если и повтор невалиден, точка считается непройденной.

### Ограничивающий ресурс — `limiting_resource`

Ресурс определяется по точке **N_max + шаг**, то есть по первой непрошедшей точке. Из всех ресурсов выбирается тот, что ближе всего к насыщению (доля от 0 до 1):

- `nvdec` — NVDEC util;
- `gpu_compute` — SM util;
- `vram` — занятая память / общий объём (равно 1.0 при OOM);
- `cpu_total` — общий CPU;
- `cpu_worker_gil` — CPU самого загруженного процесса-воркера / 100%. Под GIL один Python-процесс использует примерно одно ядро;
- `network` — трафик / скорость интерфейса;
- `stage_<имя>` — доля времени, которую поток стадии (detect/track/reid/face) был занят.

## Поиск N_max

Поиск реализован в [bench/search.py](bench/search.py), функция `find_n_max`:

1. **Ступенчатый рост.** Старт с `start` (8), затем `N ← ⌈N · growth⌉` (×1.5), пока точки проходят. Получается 8, 12, 18, 27, 41, …
2. **Бинарный поиск** между последним прошедшим и первым непрошедшим N, пока интервал не сузится до `precision` (±2 камеры).
3. Если дошли до `max_n` и точка всё ещё проходит, результат помечается `capped`: потолок не достигнут.
4. Если не прошла даже первая точка, бинарный поиск идёт вниз до 0. `N_max = 0` означает, что не выдерживается даже одна камера.

**Режим уточнения** (`--refine-from <run_id>`) берёт из грубого прохода интервал `(n_max, n_fail)`. Сначала он подтверждает нижнюю границу (при неудаче отступает вниз делением на `growth`), затем проверяет верхнюю и уточняет бинарным поиском. Так длинные 5-минутные замеры делаются только вблизи границы.

Поиск детерминирован при одинаковых ответах `evaluate`. Каждая измеренная точка сразу сохраняется в JSON, и при повторном вызове `evaluate(n)` берётся из кэша. Поэтому **возобновление после прерывания** — это просто повтор поиска: уже измеренные точки не перемеряются.

## Проход по матрице

Проход выполняет [bench/run_matrix.py](bench/run_matrix.py).

- `expand_matrix` разворачивает конфиг в список `Combo`: `scenarios × target_fps × precision × id_mode`. Для S0 точность и режим не нужны, режим идентификации нужен только для S3/S4. Затем добавляются `extra_runs`: дополнительные прогоны, где меняется **одна** переменная (например, H.265 для S0/S4 или вход детектора 1280 для S1). Дубли удаляются.
- Идентификатор комбинации выглядит, например, так: `S4_h264_fps10_int8_every_k_5`, `S1_h264_fps25_fp16_det1280`.
- Для каждой комбинации: `find_n_max` → вычисление ограничивающего ресурса → `status: done`. Комбинации со статусом `done` при `--resume` пропускаются.
- **Подтверждение.** После матрицы для комбинаций из секции `confirm` (по умолчанию S4, FP16/INT8, 10/25 FPS) выполняется длинный прогон (30 мин) на найденном N_max. Результат считается подтверждённым, если точка прошла **и** термо-троттлинга не было ни в одном сэмпле.
- Если `pipeline.mps: true`, на время прогона запускается демон CUDA MPS.
- В `results/<run_id>/` копируются исходный конфиг и `config.resolved.yaml` (после наследования и значений по умолчанию), а также пишется `log.txt`.

## Модели: экспорт и INT8-калибровка

Экспорт выполняет [models/export.py](models/export.py):

1. **ONNX.** Источник модели задаётся полем `source` в конфиге:
   - `ultralytics:yolo11s.pt` — экспорт через ultralytics с динамическим батчем;
   - `osnet:x1_0` — собственная реализация OSNet ([models/osnet.py](models/osnet.py)), совместимая по именам слоёв с torchreid. Веса берутся из `models.reid.weights`;
   - `insightface:buffalo_m/det_2.5g.onnx` — скачивание пакета InsightFace и извлечение файла; первая размерность входа делается динамической;
   - `file:<путь>` — готовый ONNX.
2. **TensorRT.** Для каждой модели и точности собирается engine с профилем `батч ∈ [1, max_batch]`. Флаг FP16 включается всегда, для INT8 дополнительно включается INT8 с калибратором `IInt8EntropyCalibrator2`.
3. **Калибровка** ([models/calib.py](models/calib.py)) идёт на реальном тестовом контенте: 1000 кадров берутся равномерно из клипов `data/videos`. Модели кропов калибруются на **настоящих кропах**: FP16-детектор находит людей, из них вырезаются тела и головы, а для ArcFace сначала работает FP16-SCRFD и выполняется выравнивание. Поэтому FP16-engine всегда собираются первыми. Кэш калибровки привязан к sha256 ONNX.
4. **Манифест** `models/engines/manifest.json` хранит для каждого engine ключ `<модель>_<вход>_<точность>` (например, `detector_640_int8`), путь, sha256 ONNX, версию TensorRT, GPU и число калибровочных образцов. Engine пересобирается, только если изменились ONNX, `max_batch` или версия TensorRT.

`pipeline/engines.py` по сценарию комбинации определяет, какие engine нужны. Если какого-то нет, бенчмарк сразу останавливается с подсказкой запустить экспорт.

Отдельный скрипт [bench/model_only.py](bench/model_only.py) измеряет **только модели** на случайных тензорах: throughput и латентность по батчам 1…256, с бэкендом TensorRT или ONNX Runtime для сравнения. Это теоретическая верхняя граница. Такой результат явно помечен как `model-only` и в карту ёмкости не попадает.

## Отчёт

[bench/report.py](bench/report.py) собирает `results/*/*.json` в `REPORT_DRAFT.md` и графики в `report/`. Для каждой комбинации берётся самый точный результат: `refine` важнее `coarse`, а при равенстве выбирается последний по времени.

Содержимое отчёта:
- окружение (GPU, драйвер, CUDA, TensorRT, PyTorch, образ);
- **таблица N_max**: строки — конфигурации, столбцы — FPS. Отметки: `+` — упёрлись в `max_n`, ✔/✘ — результат 30-минутного подтверждения;
- **N, при котором p95 ≤ 200 / 500 мс**. Значение берётся из измеренных точек без интерполяции;
- **ограничивающий ресурс** и три самых загруженных ресурса на N_max+шаг, число людей в кадре, `run_id`;
- графики «min FPS / задержка p95 / GPU util от N» и кривая «FPS на камеру ↔ N_max» для каждого сценария.

Имитационные результаты (`--simulate`) в отчёт не попадают без флага `--allow-simulated`, а если попадают, отчёт помечается плашкой «ИМИТАЦИЯ».

## Быстрый старт

Все шаги рассчитаны на запуск внутри Docker-образа на машине с GPU. Engine TensorRT привязан к версии TensorRT и к модели GPU, поэтому собирайте их там же, где проводите замеры.

```bash
# 0. Образ (TensorRT + PyTorch + PyNvVideoCodec + ffmpeg)
docker build -t h200-bench .
docker run --rm -it --gpus all --network host -v "$PWD":/workspace h200-bench bash
python scripts/env_info.py                     # проверка: GPU, драйвер, CUDA, TensorRT, NVDEC

# 1. RTSP-сервер (на хосте)
docker compose -f streamer/docker-compose.yml up -d

# 2. Тестовый контент: клипы 1920×1080@25, ≥ 5 мин, H.264 и H.265
python scripts/prepare_videos.py --download-mot20 --codecs h264,h265 --nvenc
#   или свои записи:  --src /path/to/videos
#   или уже скачанный MOT20:  --mot20 data/raw/MOT20

# 3. Модели → ONNX → TensorRT FP16/INT8
python -m models.export --config configs/matrix.yaml

# 4. (опционально) верхняя граница «только модель»
python -m bench.model_only --backend trt

# 5. Проверка обвязки на маленьком конфиге
python -m bench.run_matrix --config configs/smoke.yaml

# 6. Грубый проход всей матрицы, затем уточнение и подтверждение
python -m bench.run_matrix --config configs/matrix.yaml --measure-s 120 --skip-confirm
python -m bench.run_matrix --config configs/matrix.yaml --refine-from <run_id_грубого> --measure-s 300

# 7. Отчёт
python -m bench.report
```

`--network host` нужен, чтобы контейнер видел MediaMTX на `127.0.0.1:8554/9997`. `-v` нужен, чтобы `data/`, `models/engines/` и `results/` сохранялись на хосте.

Полезные флаги `bench.run_matrix`:

| Флаг | Назначение |
|---|---|
| `--list` | показать все комбинации и выйти |
| `--only S1,S4_h264_fps10` | только сценарии или подстроки id комбинаций |
| `--run-id X --resume` | продолжить прерванный прогон с последней точки |
| `--refine-from X` | искать только вокруг границ из прогона X |
| `--measure-s`, `--warmup-s` | переопределить длительность замера и прогрева |
| `--skip-confirm` / `--confirm-only` | без подтверждающих 30-минутных прогонов / только они |
| `--simulate` | имитация без GPU, чтобы проверить поиск, возобновление и отчёт |

### Тесты

Юнит-тесты не требуют GPU: они проверяют батчер, FPS-лимитер, трекер, планировщик идентификации, конфиг, метрики, поиск (в том числе возобновление на имитации) и отчёт.

```bash
uv sync --extra dev
uv run pytest
```

## Конфиг

Основной конфиг — [configs/matrix.yaml](configs/matrix.yaml). [configs/smoke.yaml](configs/smoke.yaml) наследует его через `base: matrix.yaml` и переопределяет только нужные ключи (слияние глубокое). Значения по умолчанию заданы в `DEFAULTS` в [bench/config.py](bench/config.py).

| Секция | Ключи |
|---|---|
| `source` | `resolution`, `codec`, `source_fps`, `video_files` (шаблон с `{codec}`) |
| `streamer` | `mode` (`local` / `external`), `rtsp_base`, `api`, `cores` (ядра для ffmpeg), `ready_timeout_s` |
| оси матрицы | `scenarios`, `target_fps`, `precision`, `id_mode`, `extra_runs` |
| `models.*` | `onnx`, `source`, `input`, `max_batch`, пороги (`conf`, `iou`, …); для `tracker` — параметры ByteTrack |
| `pipeline` | `workers`, `mps`, `batch_timeout_ms`, `queue_per_cam`, `stall_timeout_s`, `drain_s`, `face_min_person_h`, `gpu` |
| `search` | `start`, `growth`, `precision`, `warmup_s`, `measure_s`, `max_n` |
| `thresholds` | `min_fps_ratio`, `max_drop`, `max_queue_slope` |
| `confirm` | сценарии, точности и FPS для подтверждения; `duration_s` |
| `calibration` | `frames`, `batch` для INT8 |

Модели можно заменить в конфиге. Пайплайн зависит только от ONNX и адаптера пре- и постпроцессинга: для детектора это `DETECTORS` в `detector.py`, для re-ID — `NORMS` в `reid.py`.

## Важные оговорки

- **Веса OSNet.** Если `models.reid.weights` не задан, OSNet экспортируется со случайными весами. На скорость это не влияет, но эмбеддинги бессмысленны. Для замеров производительности это допустимо, экспорт выводит предупреждение.
- **Результат зависит от контента.** Нагрузка re-ID и лиц пропорциональна числу людей в кадре. Поэтому N_max привязан к плотности сцены, а в каждой точке записывается `persons_per_frame`.
- **Синтетика запрещена в итоговых результатах.** `--simulate`, `--smoke-image` и `bench.model_only` нужны только для отладки и оценки верхней границы.
- **Стример на той же машине** влияет на CPU. Поэтому ffmpeg привязывается к отдельным ядрам (`streamer.cores`), а его CPU пишется отдельно в `cpu_by_proc.streamer`.
- **GIL.** Один Python-процесс не загрузит H200, поэтому камеры делятся между `pipeline.workers` процессами. Если упор показывает `cpu_worker_gil` или `stage_track`, увеличьте число воркеров.
- [main.py](main.py) — отдельный черновой скрипт (печатает загрузку CPU через psutil) и к бенчмарку не относится.
